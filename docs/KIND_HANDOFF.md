## 4. 설계 대원칙 (몇 번 엎을 각오, 원칙만 지킨다)
1. 날짜는 전부 `calendar_day`(휴장 반영 달력) FK. 영업일 연산은 조인(`tseq`)으로만.
2. 종목 PK = 대리키 `security_id`, 코드는 `security_code` 이력. 법인(`issuer`)과 증권 분리(보통주·우선주·ETF).
3. 공시 PK = `filing_id` = `KIND:<접수번호>` / `DART:<접수번호>`. 파생 사실은 모두 근거 `filing_id`.
4. 정정은 덮어쓰지 않는다(`superseded_by`, 철회는 자기 자신). 스레드(유상증자·소각·CB/BW)는 시간순 *replay* 로 매번 재구성, `thread_key` 로 같은 event_id 유지, 안 쓰는 스레드는 `prune`.
5. 모든 적재 단계는 멱등. 스키마 변경은 마이그레이션 대신 DB 재생성.

## 5. 반드시 알아야 할 함정 (이번에 다 겪음)
- **KIND 방화벽 403(Access Denied)**: 짧은 시간에 요청이 많으면 간헐 차단. 코드는 `KindBlocked` 예외+백오프 재시도. 예전엔 403 HTML을 "0건"으로 오해해 **빈 결과가 캐시에 영구 저장**될 뻔했음(수정 완료). **전수 조회·스캔은 sleep 필수, 불필요한 호출 금지**(사용자 지침).
- **상세검색은 1년 초과 구간이면 오류 없이 0건** → 항상 ≤330일로 분할(`collector.windows`). 새 조회 코드를 쓸 때도.
- **ETF 일괄공시는 ETF 전용 엔드포인트**(`searchDisclosureByStockTypeEtfSub`)에서만 나온다. 일반 상세검색 목록엔 없음.
- 정정공시 뷰어는 *기공시 본문 + 해당 본문*을 함께 나열 → 항상 `selected` 본문 사용. 정정 전문은 마지막 "…결정 / 1. …" 이후 구간만 읽으면 최신값.
- 시장조치 필터 형식 `disclosureType02=0303|0311|`(끝에 `|`), 대분류 번호: 01 수시 02 시장조치 04 신고사항 07 발행공시.
- **DART `발행주식총수`는 발행일 기준, 우리 원장·지수는 상장일 기준** — 시드는 `발행총수 − (시드일까지 발행·이후 상장)` 으로 보정(`m1_parser.seed_adjust`). 너무 완벽하게 하지 말 것(사용자 별도 DB 보유).
- `exchange_calendars` XKRX는 2026-06-03(지방선거)·2026-07-17(제헌절) 휴장을 놓침 → `calendar_override`. 신규 휴장은 *DART 당일 공시 0건* 또는 *ETF 상장예정일 오프셋 ≠ T+1* 로 탐지.
- 우선주 종류가 여러 개(한화: 1우 `000885` 상장폐지, 3우B `00088K`) → 공시의 종류 라벨별 코드 매핑.
- DART MCP(`filing_section`)는 출력이 매우 길다(컨텍스트 소모). `find=` 로 좁히고 필요한 항목만.

## 6. 지수 규칙 (사용자 확정 3원칙 + 붙임2)
① 지수 주식수는 **신규상장일** 기준 증가(일반공모·제3자배정·CB/BW 전환·행사·합병신주) ② **주주배정 유상증자·무상증자는 권리락일**(주식배당은 배당락일) ③ **자사주 소각은 변경상장일** 감소 ④ **분할(인적)은 존속법인 변경상장일, 신설법인은 별개 종목(재상장일)** ⑤ 실권은 신주 상장일에 −실권. 2026-11 방법론 개정(현금 처리 폐지 등)은 *근거 문서 수령 후* 반영 — 첫 사례는 카카오(A035720) 분할 건 예상. 표: [`KIND_INDEX_METHOD.md`](KIND_INDEX_METHOD.md), 코드 `kind/index_rules.py`.
