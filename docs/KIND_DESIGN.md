# KIND 축(가칭 "Index Expert") 목표 설계도

작성: 2026-10-09 (개정 2026-10-09: 사용자 결정 반영, ETF 원천 확정, 캘린더 DB 구현) / 상태: **설계 확정 + 접근 검증 + 스키마·메인 캘린더 DB 구현 완료, 수집/파서 구현 전**
짝 문서: DART 축은 [`HANDOFF.md`](HANDOFF.md). 이 문서는 프로젝트의 **두 번째 축**이며, 사용자는 한국어로 소통한다.

---

## 1. 왜 KIND인가 / 두 축의 역할

| | DART 축 (완료) | KIND 축 (이 문서) |
|---|---|---|
| 발행 주체 | 기업(금감원 전자공시) | **거래소(KRX) = 시장 관리자** |
| 강점 | 사업·재무·지배구조 서술, 의사결정 공시 | **일정·수량·조치**: 주식수 변동, 상장일, 권리락, 거래정지/재개, 투자경고 기간 |
| 단위 | "이 공시가 중요한가" 판단 + 심화 분석 | "**언제 무슨 일이 일어나는가**" 캘린더·상태 추적 |
| 산출 | 종목별 대시보드 + 통합 브리프 | **일자별 이벤트 캘린더 + 상태 추적표 + 수량 변동 DB** |

핵심 구분: DART는 *판단·해석* 중심(LLM이 읽고 평가), KIND 축은 *정형 추출·추적* 중심(규칙 파서 + DB, LLM은 파서가 못 읽는 서술에만). 인덱스/패시브 자금 관점에서 필요한 "주식수·유통주식·편입비중이 언제 얼마나 바뀌는가"를 거래소 발표 기준으로 확정하는 것이 목적이다.

**예시(실측)**: SK하이닉스 `2026-06-24 유상증자결정/DR발행결정` → `07-10 정정` → `07-15 증권발행실적보고서` → `07-24 추가상장(유상증자(DR))` 공시에 *17,790,000주(제45회), 발행가 2,242,301원, 발행일 7/15, 상장일 7/29, 표준코드 KR7000660001* 이 정형으로 들어 있다. 상장일·증가 주식수는 거래소 공시에서 확정된다. 이런 **이벤트 체인(결정→신고→발행→상장)** 을 하나의 이벤트로 묶어 날짜 축에 올리는 것이 모듈 2의 목표다.

## 2. 범위 (사용자 요구 → 모듈)

| # | 모듈 | 목표 | 우선순위 |
|---|---|---|---|
| M1 | **시장조치 캘린더** | KIND '시장조치' 분류 공시를 분석해 *예정된 이벤트*를 일자별로 정리 | 1 |
| M2 | **수시공시 이벤트 체인** | 합병·분할·증자·감자·소각 등 + 거래정지·변경상장 등에 이어지는 날짜들을 한 이벤트로 묶어 정리 | 2 |
| M3 | **정지·경보 추적기** | 거래정지, 투자주의/경고/위험(및 예고), 단기과열, 공매도과열, 관리종목의 *기간·상태* 추적 | 3 |
| M4 | 대량매매 모니터(선택) | 유가증권시장 대량매매내역에서 대상 종목이 기준 이상일 때 체크 | 4 |
| M5 | ETF 좌수 DB | 대표 ETF 200 계열의 설정/해지(상장좌수) 일별 DB, 증감·트렌드 | 5 |

**범위 결정(2026-10-09, 사용자)**
- 일반 종목은 **수시공시 + 시장조치만** 본다. 신고사항은 **ETF만**. 정기·지분 등 나머지는 DART 모듈 담당.
- **주식선물·옵션 시장조치 공시는 전부 무시**한다(해당 제목 접두 `주식선물ㆍ옵션…`).
- **종속회사 관련 공시**(제목에 `(종속회사의 주요경영사항)`)는 무시한다.
- 정정공시가 반복되는 이벤트는 **최초안부터 이어 붙인 체인**으로 검수한다(최초 → 정정1 → 정정2…). 초기엔 반자동(`review_flag`).
- 분할 등 실무가 복잡한 이벤트는 단계를 좁혀 가며 사용자가 **"공시의 어느 부분을 읽을지"** 세부 지침을 준다 → 지침은 `docs/KIND_PARSE_GUIDE.md`(추후 작성)에 누적.

매 **영업일** 갱신되는 리포트가 최종 형태. 각 모듈은 개별로 돌고, 일일 리포트(§7)가 합친다.

**1단계 대상**: 삼성전자(005930, 우선주 005935 포함), SK하이닉스(000660), 삼성바이오로직스(207940). 초기 구현 후 DART 축과 같은 ~300종목으로 확장 → 종목 의존 로직은 전부 DB `watchlist` 테이블로만 받는다(초기 입력 [`kind/watchlist_phase1.json`](../kind/watchlist_phase1.json), 확장 시 DART 축의 `kospi_list_clean.md` **공유**). 확장 시 수집은 *날짜 단위 전 종목 1회 조회 후 워치리스트 필터*(요청 수 최소화).

**지수 주식수 3원칙(사용자 확정 2026-10-10)** — ① 지수 채용 주식수는 *신규상장일* 기준 증가(일반공모·제3자배정 증자는 신주 상장일) ② 기준가 조정이 있는 *주주배정 유상증자*는 *권리락일* ③ *자사주 소각*은 *변경상장일*에 감소. 구현: `kind/index_shares.py` (상장주식수 원장 + 권리락 선반영).

## 3. KIND 접근 방식 (검증 완료 2026-10-09)

**로그인·키·봇차단 없음.** 세션 쿠키 1회 획득 후 `requests`로 호출 가능(브라우저 불필요). 구현: [`kind/kind_client.py`](../kind/kind_client.py).

| 용도 | 호출 | 비고 |
|---|---|---|
| 목록(상세검색) | `POST /disclosure/details.do` `method=searchDetailsSub` | 종목 `repIsuSrtCd=A005930`, `fromDate/toDate`, `pageIndex/currentPageSize`. **헤더 `X-Requested-With: XMLHttpRequest` + 먼저 `searchDetailsMain` GET으로 쿠키 획득** |
| 유형 필터 | `disclosureType02=0303\|0311\|`, `pDisclosureType02=` 같은 값 | 값은 `\|` 구분, 끝에도 `\|`. 대분류 번호(01 수시, 02 시장조치, 03 공정, 04 신고, 05 정기, 06 특수, 07 발행, 08 지분 …)별 `disclosureTypeNN`/`pDisclosureTypeNN` |
| 오늘의 공시 | `POST /disclosure/todaydisclosure.do` `method=searchTodayDisclosureSub` `selDate=YYYY-MM-DD` | 전 종목 하루치, 필터 없이 훑을 때 |
| 본문 | `GET /common/disclsviewer.do?method=search&acptno=<접수번호>` → 본문 docNo 추출 → `POST ...method=searchContents&docNo=` → `setPath(...)`의 `/external/YYYY/MM/DD/…/*.htm` GET | 본문은 UTF-8 HTML. 표는 `\|` 평문으로 변환 |
| **ETF 공시(일괄공시 포함)** | `POST /disclosure/disclosurebystocktype.do` `method=searchDisclosureByStockTypeEtfSub`, `forward=disclosurebystocktype_etf_sub`, `etfIsuSrtCd=A069500`, `repIsuSrtCd=A069500` | 일반 상세검색(`details.do`)에는 **안 나오는** `ETF 추가ㆍ변경상장신청서(수량변경)(일괄공시)`가 여기서만 나온다. 조회기간 **3년 이내** |
| 종목 코드 해석 | `POST /common/searchcorpname.do` `method=searchCorpNameJson` | 종목명→`repisusrtcd`(A+6자리), ETF도 동일 |

**뷰어 구조(정정공시 포함)** — `disclsviewer.do?method=search&acptno=`의 `mainDoc` 선택지에는 *기공시 본문(`|N`)* 과 *해당 접수번호의 본문(`|Y`, selected)* 이 함께 나열된다. 정정공시(`[정정]…`)는 원본(들)을 앞에 달고 있으므로 **이 목록 자체가 정정 체인(최초안 → … → 현재)** 이다 → M2 체인 구성의 1차 근거(`kind_client.prior_versions`). 본문은 항상 selected 를 쓴다(첫 항목을 쓰면 원본을 받는 버그). `searchContents` 응답의 `setPath(toc, doc, …)`는 첫 인자가 비어 있지 않을 수 있다.

제약/주의
- **상세검색: 기간 1년 초과 조회 시 종목명·보고서명 등 필수 입력**(서버 정책, 2025-08). 종목 없이 전 종목을 조회할 땐 기간을 짧게. ETF 목록은 3년까지.
- 접수번호(`acptNo`, 14자리 `YYYYMMDDnnnnnn`)가 공시 고유키. 정정공시는 별도 접수번호 → 체인 연결 필요(§5).
- 서버 부하: 요청 간 0.5s 이상 sleep, 본문은 로컬 캐시(`kind/data/raw/`) 후 재요청 금지. 약관상 대량 크롤링 조건은 **미확인** → 확장 시 점검(§9).
- 목록 `size`는 100까지 정상, 페이지 순회로 전량 확보.

## 4. 모듈 상세

### M1 시장조치 캘린더
- **입력**: 시장조치(02) 유형 중 `0303, 0321, 0311, 0344, 0346, 0360, 0318, 0328, 0313`. **주식선물ㆍ옵션 시장조치 공시는 제외**(제목 접두 필터).
- **추출 필드(예)**: 권리락 → 기준가격, 적용일, 사유 / 상장 → 주식 종류·수, 발행가, 발행일, 배당기산일, **상장일**, 표준코드 / 정지 → 정지일·**해제일(또는 "변경상장일" 같은 조건부)**·사유·근거규정.
- **출력**: `events` 레코드(§6) + 일자별 캘린더 (D-day 기준 "앞으로 N영업일 내 예정"). 확정(공시된 날짜)과 조건부(날짜가 조건에 매인 것, 예: 해제일=변경상장일)를 구분 표기.
- **방식**: 공시 제목 패턴 → 템플릿별 정규식 파서. 템플릿이 정형이라 LLM 불필요. 파싱 실패 건만 LLM 폴백 + 플래그.

### M2 수시공시 이벤트 체인
- **입력 범위**: 수시공시(01)·발행공시(07, 증권신고서 계열은 일정 참고용)만. 종속회사 건 제외. 신고사항·정기·지분은 DART 모듈 소관.
- **대상 이벤트 타입**: 합병, 분할/분할합병(및 물적분할), 유상증자, 무상증자, 감자, 주식 소각, 주식 병합/분할(액면), 전환사채/교환사채 전환 상장, DR 발행, 자기주식 취득/처분, 주주명부 폐쇄/기준일, 배당.
- **체인 예시(분할, 실측: 삼성바이오로직스 2025-10~11)**: `임시주총 결과(10/17)` → `주식선물옵션 시장조치 예정 안내(10/10) → 시장조치 안내(10/20)` → `매매거래정지(분할에 따른 전자등록 변경·말소, 10/23 공시, 정지 10/30~변경상장일)` → `변경상장(회사분할(존속), 11/19)` → `변경상장 기준가격결정방법 안내(11/21)` → `주식선물ㆍ옵션 신규상장 안내(11/24)`.
- **체인 예시(유상증자, 실측: 삼성바이오로직스 2026-08~10)**: `유상증자결정(8/28)` → `증권신고서(8/28, 9/11, 10/1 정정)` → `주식선물옵션 투자유의 안내(9/4, 9/23 재안내)` → `신주발행가액(10/1)` → `권리락 기준가격 1,418,000원, 적용일 10/2(10/1 안내)` → 이후 *신주상장 예정*(발행·상장일은 후속 공시로 확정).
- **방식**: (1) 수시·발행·시장조치 공시를 `event_type` + `corp` 키로 묶는 **체인 규칙**(제목 키워드 + 시간 근접 + 본문의 동일 회차/일정), (2) 각 체인의 *날짜 슬롯*(결의일, 신고서 효력, 신주배정기준일, 권리락, 납입일, 상장예정일, 정지·재개일 등)을 채우기, (3) 빈 슬롯은 "미공시"로 남겨 추후 공시로 갱신. DART 축의 `bodies` 아카이브와 접수번호로 교차참조(OPEN DART는 10/11 18:00까지 점검).
- LLM은 본문이 서술형인 결정공시(합병·분할 계획)의 **날짜 추출 보조**에만 사용. 분할은 사용자 지침(읽을 항목 지정) 도착 후 해당 서식 전용 파서로 구현.
- **정정 체인**: 같은 (법인, 이벤트 유형, 회차) 공시는 최초안을 `initial`, 이후를 `amend`로 연결하고, 날짜 슬롯이 바뀌면 `event_date.superseded_by`로 이력 보존.

### M5 ETF 설정/해지(상장좌수) DB — 원천 확정
- **원천**: ETF 전용 목록의 `ETF 추가ㆍ변경상장신청서(수량변경)(일괄공시)`(§3). 운용사가 **그날 설정/환매가 있었던 ETF를 한 표로 일괄 공시**한다. 해당 ETF를 조회하면 그 ETF 행이 포함된 일괄공시가 나온다(실측: KODEX 200 25/25, TIGER 200 25/25, RISE 200 20/20, ACE 200 13/13건에 자기 행 포함).
- **표 구조(행당)**: 표준코드(예 `KR7069500007`, 신규 ETF는 `KR70041D0000` 알파뉴메릭) · 종목약명 · 신청수량(순증감) · 증감전 수량 · 증가 · 감소 · 증감후 수량 · 사유(설정/환매) · 추가/변경상장 예정일 · 설정 또는 환매일. 예) `TIGER 200 | -100,000 | 93,450,000 | 250,000 | -350,000 | 93,350,000 | 환매 | 2026-10-12 | 2026-10-08`.
- **날짜 의미(실측 검증)**: 설정/환매일 = T, 상장예정일 = T+1 *영업일*(36/36건 일치, 10/8 → 10/12: 10/9 한글날 휴장). 따라서 메인 캘린더의 `tseq` 연산으로 정합성 검증이 가능.
- **대표 ETF(사용자 확정, 코스피200 계열)**

- **관측 주의**: 기간 10/1~10/8 조회 시 SOL 200TR·HANARO 200·TIME 코스피액티브는 일괄공시 0건 — 해당 기간 설정/환매가 없었거나 개별 서식(`ETF 추가ㆍ변경상장신청서`, 일괄 아님)로 올릴 수 있다 → 파서는 일괄/개별 두 서식 모두 처리해야 하며, **수집 단계에서 두 서식의 존재와 누락 여부를 검증**한다(8개 ETF 일자별 커버리지 점검 리포트).
- **같은 일괄공시에 운용사의 다른 ETF 수십 개 행이 같이 실린다** → 대표 8개만 쓰지 않고 *전 행을 `etf_unit_change`에 적재*(비용 거의 동일, 후속 확장 대비). 리포트는 대표 8개 + 운용사 합계 중심.
- **산출**: 일별 좌수 시계열, 순설정(좌수·%), 5/20일 누적, 운용사별 비교, "설정 우위/해지 우위" 트렌드. 좌수 증감 × 기준가(후속) = 자금 유출입 추정. 기계적 수급 환산(좌수 증감 × 구성비)은 후속.
- **구현 결과(2026-10-09)**: 1년 백필 1,178공시 → `etf_unit_change` 54,454행, 신규 ETF 약 920종이 `security` 에 자동 등록. 검증(증감전+증감=증감후, 증가+감소=순증감, 상장일=T+1 영업일) 전부 통과. **한계**: 수집 경로가 "대표 8개가 등장한 공시"뿐이라 *대표 8개가 변동 없던 날의 운용사 일괄공시*(예: 2026-07-30 KODEX 레버리지 건)에 실린 비대표 ETF 행은 빠진다 → 비대표 ETF 전체 시계열이 필요해지면 `오늘의공시`를 날짜 단위로 훑는 수집으로 확장(§9 확장 방식과 동일). 좌수 시계열은 *변동이 있는 날만* 행이 있으므로 일별 시계열은 carry-forward 로 만든다.
- ETF의 *기타 시장안내*(`ETF기타시장안내`), 분배락, 괴리율 초과 등은 같은 목록에서 같이 수집 가능(이번엔 설정/해지 우선). 참고: 2026-10-08 KODEX 200에 **KRX 대표지수 방법론 개정 안내(KRICS 산업분류 도입, 예비종목 폐지; 적용 2026-11-02)** 가 올라왔다 → 인덱스 관점 일정으로 캘린더에 올릴 후보(지수 이벤트, 후속 모듈).

## 6. 데이터 모델 — SQLite (`kind/data/kind.db`, 정의: [`kind/schema.sql`](../kind/schema.sql))
**설계 원칙** (확장성·PK 중심)
0. **엎을 각오**: 스키마는 한 번에 완성하려 하지 않는다. 지켜야 할 것은 아래 대원칙(1~5)뿐이고, 컬럼·보조 테이블은 파서를 만들며 부족해지면 마이그레이션 대신 DB를 재생성(`rm kind.db; build_calendar; seed_master; collector; parsers`)한다 — 그러려면 **모든 적재 단계가 멱등**이어야 한다(현재 충족). 원천 본문은 `kind/data/raw/`에 캐시되어 있어 재파싱에 네트워크가 필요 없다.
1. **날짜 PK = `calendar_day.cal_date`**. 모든 날짜 컬럼은 이 테이블의 FK. 영업일 연산(T+n, 직전/다음 영업일, 구간)은 조인으로만 수행 — 휴장일 로직을 코드에 흩뿌리지 않는다.
2. **종목 PK = 대리키 `security_id`**. 단축코드·ISIN은 `security_code(code_type, code, valid_from, valid_to)` 이력 속성. 이유: 분할·병합·재상장·액면변경으로 코드가 바뀌고, ETF는 알파뉴메릭 코드(`0041D0`)이며, 공시 일부(대량매매)는 코드 없이 종목명만 준다. 법인(`issuer`)과 증권(`security`)을 분리해 보통주/우선주/ETF를 한 법인에 매단다. `issuer.dart_corp_code` 로 DART 축과 조인.
3. **공시 PK = `filing_id` = `'KIND:<접수번호>'` / `'DART:<접수번호>'`**. (DART와 KIND는 같은 문서에도 다른 번호를 매기고 번호 공간이 겹칠 수 있어 출처 접두를 PK에 넣는다. 예: 삼바 반기보고서 KIND 20260814002804 / DART 20260814003375.) 원문은 불변. 파생 사실(이벤트·주식수 원장·지정구간·ETF 좌수)은 전부 `source_acpt_no` 를 갖는다 → 항상 원문으로 되짚기.
4. **정정은 덮어쓰지 않는다**: `superseded_by`로 이력 보존, 현재값은 `superseded_by IS NULL`.
5. 워치리스트도 테이블(`watchlist`) → 3종목 → 300종목 확장은 행 추가.

### 6.1b M1 구현 결과 (2026-10-10)
- **서식은 모두 정형**이라 정규식으로 충분했다(LLM 불필요). 변경상장은 `변경전 → 변경후 / 변경주식수 / 변경상장일 / 발행일(소각일) / 표준코드(종류별)`, 추가상장은 `주식의 종류와 수 / 발행가액 / 발행일 / 상장일`, 기준가격 안내는 `번호 항목: 회사명·주권종류와 가격·사유·적용일`, 거래정지는 `정지일·해제일·사유`.
- **원장 검증(이중 체크)**: ① 공시의 `변경전 → 변경후`가 직전 잔고와 이어지는지(`chain_break`), ② DART 시드(2026-06-30)와 이어지는지(`seed_mismatch`). 삼성전자 소각 후 5,846,278,608 · 우선주 802,371,203 · SK하이닉스 소각 후 712,702,365 · 삼바 분할 후 46,290,951 이 모두 DART 반기 수치와 **정확히 일치**. DR 추가상장(+17,790,000, 상장 7/29)은 공시에 잔고가 없어 `is_computed=1` 로 730,492,365 를 계산.
- **날짜 의미 주의**: 원장의 `effective_date`는 *변경상장일*(주식수가 시장에 반영되는 날)이고 `issue_date`(발행·소각일)와 다르다(삼전 소각 4/2 → 4/14, 하이닉스 2/9 → 2/23). 지수/패시브 관점에서는 변경상장일이 기준.
- **조건부 날짜 해소**: 삼바 분할 정지의 해제일이 `변경상장일`이라는 *조건*으로만 공시됨 → 변경상장 공시의 `매매거래정지가 해제됨` 문구로 같은 종목의 열린 HALT 를 확정(2025-10-30 ~ 2025-11-24). 조건부 값은 `condition_note` 로 남고 확정 시 `superseded_by` 로 이력 보존.
- **우선주**: 삼성전자우 기준가격 안내는 제목 `(삼성전자우)` + 종류 `1우선주`로 구분. 우선주 ISIN(KR7005931001)은 변경상장 공시의 `표준코드`에서 자동 보충.
- 수집 중 발견: 종목 지정 상세검색도 *기간이 1년을 하루라도 넘으면 0건*을 반환(오류 없이). → 330일 단위로 쪼개 조회(`collector.windows`). **조용한 0건**이므로 신규 0건이 연속되면 의심하는 점검을 일일 파이프라인에 넣을 것.
- 재생성: `kind/rebuild_all.sh` 한 번으로 캘린더 → 시드 → 수집 → ETF 파서 → M1 파서 → 리포트(본문은 캐시 사용).

## 7. 일일 파이프라인 (영업일)
1. **수집** (장 종료 후 ~20:40 이후 + 익일 07:30 점검): 대상 종목 × (시장조치 + 수시 + 발행 + 공정) 신규 공시 → `filings`. 투자경고 지정 등은 **20:00 전후**, 대량매매·ETF류는 **20:07~20:30** 게시되므로 20:40 이후가 안전.
2. **분류·파싱**: 제목 → 템플릿 → 정규식 파서 → `events/event_dates/designations/share_changes`. 미분류/파싱실패는 `review` 큐.
3. **추적 갱신**: 상태 머신 전이, 예정 이벤트 D-day 갱신, 해제·종료 확정.
4. **리포트**: (a) 오늘 신규 공시 요약, (b) **향후 N영업일 이벤트 캘린더**, (c) 정지·경보 현황표(남은 기간), (d) 주식수 변동 원장 증감, (e) (M4/M5) 대량매매·ETF 좌수 증감. 형식은 DART 축과 같은 HTML→PDF(`report_v2/` 렌더러 재사용 검토) + 인덱싱용 MD.
5. DART 축 `run_daily.py` 에 후속 단계로 붙이거나 별도 launchd 작업으로 분리(§9 결정).

### 남은 이슈
1. **ETF 서식 두 종류**: `일괄공시` 외에 개별 서식이 있는지(SOL 200TR·HANARO 200·TIME은 최근 일괄 0건) — 수집 시 일자별 커버리지로 검증.
2. **상장주식수 원천의 선행성**: M4(0.5% 판정)에 필요. 초기값(기준 시점의 상장주식수)을 어디서 잡을지 — DART 사업/분기보고서의 주식 총수 또는 KIND 종목정보 페이지(`corpdetail`)로 시드하고 이후 `share_ledger`로 증감. 결정 필요(제안: DART MCP `company`/`filing_section`으로 3종목 시드).
3. **우선주·다종목**: 삼성전자우(005935) 등 — `security` 분리 모델로 해결. 시장조치는 종목별 공시가 따로 올라오므로(예: 배당락 기준가격 안내가 보통주/우선주 각각) 매핑 필요.
4. **삼바 분할 단절**: 2025-11 분할 후 *존속법인* 기준 가격·주식수가 단절 → `기준가격 결정방법 안내`를 보정 이벤트로. 사용자 지침 대기.
5. **약관/부하**: KIND 자동수집 허용 범위 불명확. 요청 간 sleep + 본문 캐시 + 날짜 단위 조회로 최소화. 상용 확장 전 재점검.
6. **DART 축 통합 방식**: 같은 PDF 브리프에 섹션 추가 vs 별도 KIND 리포트. (OPEN DART 점검 종료 10/11 18:00 이후 크로스체크 가능.)
7. 캘린더 `confidence='unverified'` 구간(2027-10-09~) 갱신 일정.
