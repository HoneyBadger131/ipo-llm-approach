## 3. 설계 판단과 발견

1. **날짜의 90%는 결정 공시 하나에 들어 있다.** 유상증자결정에 기준일·청약·납입·상장예정·일반공모·신주수·예정발행가·배정비율이 모두 있고, 정정공시도 *정정 반영된 전문*을 포함하므로 마지막 전문 구간만 읽으면 항상 최신값이다.
2. **예외: 신주인수권증서 거래기간.** 결정 공시에는 `증서 상장 여부(예)`만 있고 기간은 **증권신고서/투자설명서**(수집 범위 밖: 발행공시)에만 있다. 상장이 임박하면 시장조치로 `신주인수권증서 신규상장`(상장일·폐지일·증서수·청약기간)이 올라오므로 그것이 확정 소스. → **온디맨드 규칙**: 스레드에 증서 일정이 없을 때만 해당 법인의 `투자설명서`를 조회해 "상장기간은 A부터 B까지", "C에 상장폐지될 예정"을 읽는다(삼바 10/26~10/30, 폐지 11/2). 투자설명서는 85만자라 목록만 필터해 최신 1건만 받는다. (결정 후 시장조치 공시가 나오면 값이 교체된다.)
3. **증서 거래종료일과 상장폐지일은 다르다.** 폐지일은 마지막 거래일 다음 영업일(한화 7/10 → 7/13, 삼바 10/30 → 11/2). 코드는 `거래종료 = 폐지일의 직전 영업일`로 맞추고 투자설명서의 문구와 교차 확인.
4. **정정이 잦다 — 한화솔루션.** 같은 증자가 정정 7회: 신주 7,200만주×33,300원(2.40조) → 5,600만주×32,400원 → (5/12 일정 미정) → 5,300만주 → 1차 27,900원 → 최종 22,100원(조달 1.171조원, 시설자금 9,077억 + 채무상환 2,636억). 날짜가 바뀔 때마다 이전 값은 `superseded_by`로 보존, '일정 미정'처럼 날짜가 사라지는 정정은 자기 자신을 supersede하는 *철회 표시*로 남긴다. 지수 관점 핵심: 권리락 시점(6/15)에 유효했던 수량(5,300만주)을 기준으로 반영하고, 이후 발행결과(5,300만주 실발행)와 대조.
5. **권리락일 규칙 검증**: 기준일 → 권리락일 계산이 실제 권리락 공시와 **2건 모두 일치**(삼바 10/6→10/2, 한화 6/16→6/15). 삼바는 기준일이 10/5 대체공휴일 다음날이라 "기준일 -1일"이 아니라 "직전 영업일"이어야 맞는다.
6. **금액 정합성 검사**: `신주수 × 발행가 = 자금용도 합계`가 3건 모두 일치(삼바 2.66498조, 한화 1.1713조, SK하이닉스 40.02조). 한 쪽만 정정되고 다른 쪽이 안 바뀌면 불일치로 드러난다.
7. **제3자배정(SK하이닉스 ADR)**: 일반 제3자배정과 달리 국내 배정 대상이 없고 해외 예탁기관에 신주 전량을 발행(ADR 상장 공모). 결정 시 수량은 "최대 한도", 발행가·자금은 가격결정 후 정정으로 확정(결정 40.02조 → 실제 발행 39.89조). 지수 효력일은 신주 상장일(7/29)로 규칙대로 처리됨.
8. **상장주식수 원장과 지수 주식수는 다른 축**이다. 원장(`share_ledger`)은 신주 상장일에 늘고, 지수(`index_share_adj`)는 권리락일에 이미 늘어 있다. 삼바 10/8 기준 원장 46,290,951주 vs 지수 48,560,951주. 신주 상장일에 두 값이 같아진다.

## 4. 구현 구조

```
유상증자결정 파싱(정정 포함) ─┐
유상증자 신주발행가액(안내) ──┤
권리락 기준가격 안내(M1) ─────┤  시간순 replay → event_date 슬롯(정정 이력 보존)
신주인수권증서 신규상장 ──────┤                 → event.detail_json(규모·발행가·구주주·이력)
청약결과 / 발행결과(자율) ────┤                 → index_share_adj(지수 주식수 증가일·수량)
추가상장(유상증자…) (M1 원장) ─┘                 → share_ledger.event_id 연결
투자설명서(온디맨드, 증서 일정 없을 때만)
```
- 스레드는 매 실행 처음부터 replay로 재구성(같은 `event_id` 유지) → 멱등. 재실행 3회 건수 동일 확인.
- 후속 공시는 "같은 법인에서 직전에 시작된 스레드"에 붙인다(동시 진행 스레드가 생기면 규칙 보강 필요).

## 6. 한계 · 다음에 확인할 것

1. **지수 수량 기준**: 권리락일에는 공시 신주수로 선반영하고, 신주 상장일에 실제 상장 수량으로 교체(실권 시 감소) — 방법론 (붙임2)로 확인됨(`KIND_INDEX_METHOD.md` 3절). 4개 사례는 모두 실발행 = 결정 수량이라 조정 0.
2. **삼바는 아직 진행 중** — 신주인수권증서 상장(10/26)·최종 발행가 확정(11/5 공시)·청약 결과 등은 공시가 올라오면 자동 반영되는지 *실제 흐름으로 재확인* 필요(한화 사례로는 파서 검증됨).
3. **무상증자·감자·소각·합병·분할**은 아직 별도 트랙(다음 지침 항목). 같은 스레드 틀(`thread_key`, 슬롯, `index_share_adj`)을 재사용할 수 있게 만들었다.
4. 우선주 배정(우선주가 있는 회사의 유증)·`주주우선공모`·`일반공모`는 서식 미관측이라 `OTHER`/review로 처리.
5. 자금 사용 목적은 "가볍게" 요구에 맞춰 규칙 기반 한 줄(타법인 증권취득만 대상회사 확인). 시설자금의 세부 투자처(예: 한화 시설자금 9,077억)는 `신규시설투자등` 공시 연결이 필요하면 후속.
6. 온디맨드로 읽는 발행공시(투자설명서)가 수집 범위(수시·시장조치) 밖 예외임을 설계서에 명시함. 300종목 확장 시 대상 스레드에 한정되므로 요청 수 증가는 작다.

### 7.1 지수 주식수 3원칙 (사용자 확정) → [`kind/index_shares.py`](../kind/index_shares.py)
| # | 원칙 | 구현 |
|---|---|---|
| 1 | 지수 채용 주식수는 **'주식의 신규상장일'** 기준으로 증가. 증자(일반공모·제3자배정)는 **신주 상장일** | 원장(`share_ledger`)은 변경·추가상장 공시의 상장일/변경상장일 기준 → 그대로 충족. 트랙 `THIRD_PARTY`·`PUBLIC`(일반공모) = 신주 상장일 (일반공모는 이전엔 "검토" 처리였으나 정식 트랙으로 변경) |

| 3 | **자사주 소각**은 **변경상장일**에 감소 (결의 → 소각예정일 → 변경상장 공시 → 변경상장일) | 원장 `effective_date` = 변경상장일(`issue_date`=소각일은 별도 보존). 삼성전자 소각: 소각일 4/2, 변경상장일 4/14 → 지수 주식수는 **4/14**에 감소(4/13 5,919,637,922 → 4/14 5,846,278,608) |

`index_shares(sid, 기준일)` = 상장주식수(원장) + 선반영(권리락일 ≤ 기준일, 해당 신주의 상장 행이 아직 없는 증자). 일일 리포트 1절에 *상장주식수*와 *지수 반영 주식수*를 나란히 표시(삼바 46,290,951 vs **48,560,951**).
버그 수정: 신주 상장 *예정일*이 지났는데 상장 공시가 아직 없는 경우(삼바 11/30 이후 가정) 선반영이 빠져 지수가 되돌아가던 문제 → 상장 행이 실제로 생길 때까지 유지.
